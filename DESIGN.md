# AppBoilerplate — Design Document

## Overview

A template repository boilerplate for scaffolding React Native mobile apps, built on **Expo (dev builds)** + **Convex backend**, organized as a **Turborepo monorepo** with **pnpm**.

- **Distribution:** Template repo (clone/fork). No interactive CLI.
- **Audience:** Private use first, open-source later.
- **Platforms:** iOS 15+ / Android SDK 24+

## Provider Stack & Data Flow

### Provider Hierarchy (`app.tsx`)

```
ConvexProviderWithAuth
  └── ThemeProvider
      └── I18nextProvider
          └── NavigationContainer (with linking config + theme)
              └── RootNavigator
```

### Data Flow Patterns

1. **Server state (Convex):** Components call `useQuery()` and `useMutation()` directly. Real-time by default — no cache invalidation needed.
2. **Client state (Zustand):** UI-only state. `useSettingsStore` persists theme/language preferences to AsyncStorage. `useAuthStore` caches lightweight session info.
3. **Auth flow:**
   - `RootNavigator` checks Convex Auth session state
   - Unauthenticated → `AuthNavigator` (Login, Register)
   - Authenticated → `MainNavigator` (Tabs: Home, Profile, Settings)
   - Convex Auth handles token management internally
4. **Navigation + Deep linking:** `linking.ts` maps URL schemes to screens. React Navigation handles state restoration.

### Import Rule

Features never import from other features. They only import from `shared/` or call Convex functions directly.

## Environment Management

```
.env.development        # Local dev (gitignored)
.env.staging            # Staging (gitignored)
.env.production         # Production (gitignored)
.env.example            # Committed — documents required vars
```

- `app.config.ts` reads `process.env` and exposes values via `Constants.expoConfig.extra`
- `shared/env/index.ts` exports a typed `env` object for type-safe access
- EAS build profiles in `eas.json` map to environments, injecting the matching `.env.*` file

## Push Notifications

- `expo-notifications` with permission request helper
- Registration stores Expo push token in Convex (`users` table mutation)
- `useNotifications` hook handles foreground display and tap navigation
- No server-side push sending — client-side plumbing and token storage only

## Splash Screen

- `expo-splash-screen` configured in `app.config.ts`
- `SplashScreen.preventAutoHideAsync()` at app entry
- Hidden after providers are ready and auth state is resolved
- Custom splash image in `assets/splash.png`

## Testing

### Unit Testing

- Jest + `@testing-library/react-native` in `apps/mobile/`
- `convex-test` in `packages/backend/`
- Sample test per feature
- Turborepo `test` pipeline runs both in parallel

### E2E Testing (Maestro)

```
.maestro/
├── auth/
│   ├── login.yaml
│   └── register.yaml
├── home/
│   └── browse-items.yaml
└── config.yaml
```

- Organized by feature, mirroring `features/` structure
- Runs against Expo dev build on simulator
- Separate from Turborepo pipeline (requires running app)

## CI/CD — GitHub Actions

### `ci.yml` (push to main, pull requests)

1. `pnpm install`
2. `turbo lint`
3. `turbo test` (unit: mobile + backend)
4. `turbo build` (type-check both workspaces)

### `e2e.yml` (manual / nightly)

1. Build Expo dev client on simulator
2. Run Maestro flows

E2E is separate — too slow for PR checks. `turbo build` in CI serves as a type-check gate, not an app binary build.

## DX Tooling

- **ESLint:** Root config extends `@react-native`, `prettier`, `plugin:react-hooks`. Workspaces inherit.
- **Prettier:** Root `.prettierrc` for consistent style.
- **Turborepo pipelines:** `lint`, `test`, `build`, `dev` — parallel execution across workspaces.

## Decision Log

| #   | Decision                    | Alternatives Considered                | Rationale                                                          |
| --- | --------------------------- | -------------------------------------- | ------------------------------------------------------------------ |
| 1   | Expo-only (no bare RN)      | Expo + bare RN CLI                     | Simpler scope, dev builds cover native module needs                |
| 2   | Convex moderate integration | Minimal / Full integration             | CRUD + auth + real-time demonstrates patterns without overwhelming |
| 3   | React Navigation            | Expo Router                            | User preference; imperative control, more flexible                 |
| 4   | Template repo (no CLI)      | Interactive CLI, CLI + config flags    | Lower maintenance, simpler to start; CLI can come later            |
| 5   | Convex Auth                 | Clerk + Convex, both as option         | Fewer dependencies, tighter Convex integration                     |
| 6   | Zustand for client state    | React built-ins, no prescribed pattern | Lightweight, minimal boilerplate, scales well                      |
| 7   | Flat Feature Modules        | Domain packages, layered architecture  | YAGNI — simplest structure that scales; extract later if needed    |
| 8   | Turborepo + pnpm            | Yarn/npm workspaces only, yarn berry   | Fast caching, excellent monorepo DX, strict dependency management  |
| 9   | Maestro for E2E             | Detox                                  | YAML-based simplicity, great Expo dev build support                |
| 10  | ESLint + Prettier           | Biome, ESLint + Prettier + Husky       | Widely supported, familiar; no pre-commit hooks to reduce friction |
| 11  | GitHub Actions only         | + EAS Build, + EAS Submit              | Keep CI simple; EAS available for manual use via eas.json          |
| 12  | iOS 15+ / Android SDK 24+   | More modern targets                    | Reasonable defaults, broad device coverage                         |
| 13  | E2E in separate CI workflow | Blocking on PRs                        | Too slow for PR checks; nightly/manual is pragmatic                |

## Assumptions

- Convex Auth is mature enough for needed auth patterns (email/password, OAuth)
- Turborepo structure: `apps/mobile` and `packages/backend`
- No OTA updates (EAS Update) in scope
- Template repo: users clone/fork and remove what they don't need
- Dark/light theming uses React Navigation's built-in theme + custom theme context
- Push notifications use `expo-notifications` with basic setup, not a full notification service
